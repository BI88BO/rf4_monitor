# 渔获按饵料汇总报表 — 设计

日期：2026-08-07
状态：已获用户批准

## 目标

把每次自己上鱼（入护 / 脱钩 / 放生）的记录，按"饵料"汇总成账本，并随会话写入 CSV 文件，便于查看每条鱼都是吃什么饵钓到的。

## 核心假设

同一段会话（一次钓鱼连接）内，玩家不会中途更换饵料，饵料恒定。因此只需在会话内识别出"当前饵料"一次，之后所有上鱼都归因到该饵料。

## 术语

- 饵料 key：游戏内部资源 key，形如 `dough_garlic`、`worm_*`、`bait_*`、`pellet_*`。
- 合成事件：bridge 为"自己上鱼"合成的 `SyntheticChatEvent`，含阶段（incoming/bitten/kept/escaped/released）与重量。

## 架构与组件

### 1. 饵料识别（两条来源，互为兜底）

- **主来源**：装备/物品帧（如 4/22）的 ascii 字符串，挑出以 `dough_` / `worm_` / `bait_` / `pellet_` 前缀开头的 key 作为饵料。
- **复核来源**：结算/入护响应帧的 ascii 串（bridge 现有日志已能打印出 `dough_garlic` 的位置）提取一次，若不同则更新当前饵料。
- 首次命中后存入 `session.current_bait_key`，此段会话内沿用。

实现时需实测确认：挂饵时具体是哪个帧带出饵料 key。优先查 4/22 装备帧与结算帧；若都取不到，再扫描其它帧。

### 2. 渔获账本（按饵料聚合）

在 `FlowSession` 新增账本字段：

```
current_bait_key -> {
    kept_count,     # 入护条数
    escaped_count,  # 脱钩条数
    released_count, # 放生条数
    kept_weight_g,  # 入护重量合计(g)
    total_count,    # 总条数
}
```

在合成事件发出处（`_emit_self_event` 附近）统一记账：
- 入护（kept）：条数 +1，重量计入 `kept_weight_g`。
- 脱钩（escaped）/ 放生（released）：仅条数 +1。
- incoming / bitten：不计入（还没定结果）。

### 3. CSV 落盘

- 会话结束时（bridge 收到会话结束/连接关闭时）写 `logs/渔获统计.csv`。
- 列：`饵料,入护,脱钩,放生,重量合计g,总条数`。
- 跨会话合并：写前先读旧 CSV，若同一饵料已存在则叠加本次会话增量，再写回。

### 4. 饵料显示名

- 优先用 `game_catalog` 本地化表（若收录）显示中文名。
- 未收录时显示原始 key。

## 明确不做（范围外）

- 不做浮窗实时显示（已选定 CSV 报表形式）。
- 不做换饵分段（会话内饵料恒定；换饵会触发重连新会话）。
- 不解析饵料来源帧内的精细字段，仅做 ascii key 提取。

## 错误处理

- 会话内始终未识别到饵料：所有鱼归入 `unknown` 单列一行，不阻断统计。
- CSV 写入失败（权限/占用）：记录日志，不崩溃。
- ascii 提取到多个候选饵料 key：取第一个；后续复核帧发现新 key 才覆盖。

## 测试

- 单元级：ascci 饵料 key 识别函数，覆盖 `dough_garlic` / 非饵料字符串 / 无匹配。
- 集成级：模拟一个会话的 kept/escaped/released 合成事件，验证账本计数与重量合计正确。
- CSV：验证跨会话合并与新增条目。
